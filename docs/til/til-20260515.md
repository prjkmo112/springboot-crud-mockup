## 1. JPA N+1 문제란?

`Order` 목록을 조회할 때, 각 주문에 연결된 `Product` 정보를 가져오기 위해 **N개의 추가 쿼리**가 발생하는 현상이다.

예를 들어 주문이 100개 있으면:

- 주문 목록 조회 쿼리 1번
- 각 주문의 상품 조회 쿼리 100번

→ 총 **101번** 쿼리가 실행된다.

```java
// Order 엔티티 - LAZY 로딩 설정
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "product_key", referencedColumnName = "product_key")
private Product product;
```

`FetchType.LAZY`로 설정되어 있으면, `order.getProduct()`를 호출하는 순간마다 DB를 조회한다. 목록을 반복하면 N+1이 터진다.

---

### 1-1. JOIN FETCH로 해결하기

`OrderRepository`에 JPQL `JOIN FETCH`를 사용해서 Order와 Product를 **한 번의 쿼리**로 함께 가져오도록 수정했다.

**수정 전:**

```java
// 단건 조회 시 product를 별도로 가져옴 → 단건이라도 쿼리 2번
Optional<Order> findByOrderKey(String orderKey);
```

**수정 후:**

```java
// JOIN FETCH로 product를 함께 조회 → 쿼리 1번
@Query("SELECT o FROM Order o JOIN FETCH o.product WHERE o.orderKey = :orderKey")
Optional<Order> findByOrderKeyWithProduct(@Param("orderKey") String orderKey);
```

목록 조회용 쿼리도 같은 방식으로 `JOIN FETCH`가 적용한다.

```java

@Query(value = "SELECT o FROM Order o JOIN FETCH o.product",
        countQuery = "SELECT count(o) FROM Order o")
Page<Order> findAllWithProduct(Pageable pageable);
```

> **주의:** `countQuery`는 따로 지정해줘야 한다. `JOIN FETCH`가 포함된 쿼리를 그대로 count에 쓰면 오류가 난다.

그리고 `OrderService`에서 단건 조회 메서드를 정리했다.

**수정 전:** 공통 헬퍼 메서드 `getOrderEntityByOrderKey()`가 product를 로딩하지 않아 조회 시 N+1 발생

**수정 후:** 조회 목적에 따라 메서드를 분리

- 단건 조회 (`getOrderItem`) → `findByOrderKeyWithProduct` 사용 (product 함께 로딩)
- 삭제 (`deleteOrder`) → `findByOrderKey` 사용 (product 불필요)

```java
// 조회 시: product 포함
@Transactional(readOnly = true)
public OrderDto getOrderItem(String orderKey) {
    Order order = orderRepository.findByOrderKeyWithProduct(orderKey)
            .orElseThrow(() -> new IllegalArgumentException("order not found"));
    return OrderMapper.INSTANCE.toDto(order);
}

// 삭제 시: product 불필요
@Transactional
public void deleteOrder(String orderKey) {
    Order order = orderRepository.findByOrderKey(orderKey)
            .orElseThrow(() -> new IllegalArgumentException("order not found"));
    orderRepository.delete(order);
}
```

## 2. DB FK vs 애플리케이션 레벨 연관 관계

`orders` 테이블의 `product_key` 컬럼을 `products` 테이블의 `product_key`에 DB foreign key로 설정하는 것이 자연스러울 수 있다.
하지만 fk에 따르는 단점을 분명히 파악하고 사용을 해야한다.

**DB FK의 단점:**

- **배포/마이그레이션 순서 제약** — FK가 걸린 테이블을 수정할 때 참조 테이블 순서를 맞춰야 해서 스키마 변경이 까다로워진다
- **테스트 데이터 삽입 불편** — 테스트 시 참조 대상 데이터를 먼저 넣어야 해서 구성이 복잡해진다
- **DB 확장 시 제약사항** — 나중에 `products`와 `orders` 테이블이 서로 다른 DB로 분리될 경우, DB 레벨 FK는 애초에 불가능하다
- **FK 검증 오버헤드** — 대량으로 데이터를 쓸 때마다 DB가 무결성을 검증하기 위해 부모 테이블의 인덱스를 매번 조회해야하고 lock을 해야한다. fk 를 설정할 때 가장 고려해야하는 병목이 될 수 있는
  부분이다.

> 만약 fk를 사용하지 않기로 결정했다면 무결성 보장은 애플리케이션 레벨에서 보장 해줘야 함

```java
// 주문 생성 시, productKey가 실제 존재하는지 직접 검증
Product product = productRepository.findByProductKey(createOrderDto.getProductKey())
                .orElseThrow(() -> new IllegalArgumentException("product not found"));
```

JPA 연관 관계는 조회(JOIN) 용도로만 사용하고, 실제 FK 역할은 하지 않도록 `insertable = false, updatable = false`로 선언했다.

```java
// Order 엔티티 — product 필드는 읽기 전용 연관, DB 컬럼 쓰기에는 관여하지 않음
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "product_key", referencedColumnName = "product_key",
        insertable = false, updatable = false)
private Product product;

@Column(name = "product_key", nullable = false, length = 64)
private String productKey; // 실제 저장은 이 필드로
```

`product_key` 값은 `productKey` String 필드로 저장되고, `product` 필드는 `JOIN FETCH` 시에만 사용된다. DB에 FK 제약은 없지만, 서비스 레이어에서 존재 여부를
검증하므로 잘못된 `product_key`가 저장되는 일은 막을 수 있다.

## 3. 재고 차감 로직 구현

`Product` 엔티티에 `stock` 필드를 추가하고, 주문 생성 시 재고를 차감하는 로직을 구현했다.

```java
// Product 엔티티에 재고 필드 추가
@NotNull
@Column(name = "stock", nullable = false)
private Integer stock;
```

주문 생성 시 재고 검증 및 차감:

```java

@Transactional
public OrderDto createOrder(CreateOrderDto createOrderDto) {
    Product product = productRepository.findByProductKey(createOrderDto.getProductKey())
            .orElseThrow(() -> new IllegalArgumentException("product not found"));

    // 재고 검증
    if (product.getStock() <= 0) {
        throw new IllegalStateException("product out of stock");
    }

    Order order = OrderMapper.INSTANCE.fromDto(createOrderDto);
    order.setId(null);
    product.setStock(product.getStock() - 1); // 재고 차감
    order.setCreatedAt(LocalDateTime.now());

    Order savedOrder = orderRepository.save(order);
    return OrderMapper.INSTANCE.toDto(savedOrder);
}
```

> **@Transactional이 중요한 이유**  
> 재고 차감과 주문 저장은 하나의 트랜잭션으로 묶여야 한다. 주문 저장에 실패하면 재고 차감도 롤백되어야 하기 때문이다. `@Transactional`이 없으면 재고만 줄고 주문은 안 생길 수 있다.
>
> 또한 JPA의 Dirty Checking 덕분에 `productRepository.save(product)`를 명시적으로 호출하지 않아도, 트랜잭션 커밋 시점에 변경된 `stock` 값이 자동으로
> DB에 반영된다.
